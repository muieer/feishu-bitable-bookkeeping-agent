# 系统架构与工作流程

应用以一条完整文字消息为单位，固定执行「识别 → 校验与编号 → 决策 → 校验与执行 → 结果」流程。无消费消息在识别后结束。模型负责语义理解，程序拥有执行权。

## 模型与程序边界

| 环节 | 输入 | 输出或校验 |
| --- | --- | --- |
| 阶段一 LLM | 完整消息、窗口内结构化账单 | `RecognitionResult.items`：类型、已有目标编号、规范化原文 |
| 程序识别校验 | 第一阶段输出 | 拒绝未知或重复目标、额外字段、虚构或重叠来源；按识别顺序为新消费编号 |
| 阶段二 LLM | 编号后的消费、原消息发送时间、相关已有账单、完整分类知识 | `MessagePlan.decisions`：每个编号对应一个 `create`、`update` 或 `clarify` |
| 程序决策校验 | 第二阶段输出 | 编号集合一一对应，原文不变，行为与识别类型一致 |
| 程序逐笔校验 | 新账单或原成功快照合并修改字段 | 完整日期、正数金额、最多两位小数、消费内容、合法完整分类路径 |
| 执行 | 通过校验的消费 | 预检表结构，批量新增；更新先核对远端，只提交变化字段 |

两个阶段不共享模型对话历史，也不开放模型可调用的业务工具。第一阶段不注入分类知识；第二阶段每次注入完整分类树和规则，已有消费仅用于理解自身修改，不查询历史案例和长期偏好。系统提示词明确要求忽略输入数据中改变职责或输出协议的指令。

第一阶段 `raw` 仅允许空白和人民币符号规范化。程序在规范化后的完整消息中顺序定位各片段，防止虚构、重叠和重复识别。相同原文真实出现两次时可各识别一项；同一笔交易的商品明细与总额是否属于一笔，由第一阶段模型按语义识别。

## 编号与上下文

上下文按 `(user_id, chat_id)` 隔离，默认空闲 `1800` 秒后过期。每个窗口从 `B1` 起递增编号；已有消费沿用原编号，新消费按识别顺序分配，已分配编号不回收。列表中的 `1.`、`2.` 仅用于排版，关联目标使用 B 编号，不依赖上一次回复的列表位置。

程序维护 `bill_id → Bill → record_id`，模型不返回或决定远端 `record_id`。账单上下文包含编号、本次原文、消息时间、状态及已成功确认的完整账单。第二阶段只提供与本次 `existing` 项相关的旧账单。

未写入消费也保留编号和结果。`clarify` 不保存部分消费字段，不维护等待补充的草稿或问题，不自动续填。没有成功快照的已有编号不能执行 `update`；结果不确定的编号也不能再次提交写入。窗口过期或服务重启后短期编号失效，持久化去重状态继续生效。

## 三种决策与执行状态

| 决策 | 必填约束 | 执行 |
| --- | --- | --- |
| `create` | `expense` 四字段全部存在，`reason=null` | 校验完整账单后新增 |
| `update` | 仅明确修改字段非空，其他字段显式 null；`reason=null` | 与原成功快照合并，完整校验；远端预检后只更新变化字段 |
| `clarify` | `expense=null`，`reason` 为具体非空原因 | 不写入，不追问，不保存待补充事实 |

模型决策与程序结果分开。程序状态只有 `success`、`clarified`、`failed`、`uncertain`：

- `success`：写入响应及对应记录 ID 已确认，或测试模式准备完成。
- `clarified`：模型选择不写入，仅保留原因。
- `failed`：业务校验或执行前检查失败，尚未提交这笔写入。
- `uncertain`：已经保留写入操作，但响应无法可靠确认，不自动重试。

结构化输出整体无效时，本条消息不执行写入。通过结构校验后，业务合法性按笔检查：一笔金额无效、分类无效、更新目标未成功或远端被外部修改，不阻止其他合法消费。新消费批量提交，逐笔确认；无法逐笔对应的响应标记待核对。

## 防重复与更新检查

同一会话从理解到执行串行，同一表的写入也串行。执行前原子保存消息与逐笔操作保留；操作 ID 包含消息 ID、B 编号和动作，避免上下文重置后 B 编号重用造成持久化冲突。

新增响应必须有正确数量的非空、唯一记录 ID，且不能忽略字段。更新前通过 `+record-get` 核对远端账单是否与原成功快照一致；存在外部变化或记录无法读取时不提交修改。更新响应必须准确对应目标记录 ID，且不能忽略字段。成功响应作为确认依据，不做写后回读。

写入超时、取消、异常响应和返回映射不完整均保守处理。`started` 或 `uncertain` 保留禁止重放，消息重投、回复失败或服务重启不会重复执行。远端已确认但本地成功状态保存失败时，保留成功事实并提示本地状态问题。

## 结果与耗时

正常分组顺序固定为新增、更新、澄清，各组按 B 编号数值升序排列。执行失败和待核对另列，不混入模型澄清。成功账单统一为：

```text
B编号：YYYY/MM/DD｜一级分类｜二级分类｜三级分类（如有）｜具体｜金额元
```

三级为空时省略。卡片采用纯文本，处理期间只显示「已耗时 N 秒」，每秒尝试刷新。处理结束后停止中间更新，显示完整分组结果。反馈送达失败只重试反馈，不重试业务写入。

## 模型请求预算与日志

单条消息两阶段共享一个发送预算，上限 `10`，可通过 `LLM_MESSAGE_REQUEST_LIMIT` 降低，不能提高。每阶段最多两次模型请求，包括一次输出重试；HTTP SDK 重试和重定向另在发送边界计数。可选 `LLM_HTTP_REQUEST_LIMIT` 和持久化预算文件进一步限制整个验证过程的总发送次数。

消息日志记录两阶段完整提示词、输入、Schema、输出、重试和实际 HTTP 通信；凭证字段和已知密钥脱敏。处理阶段仍写入调试日志，但不展示在卡片中。日志无法落盘时阻止新的模型请求和业务写入；已提交操作继续尽力确认结果。日志删除后可恢复后续写入，不补造历史事件。
