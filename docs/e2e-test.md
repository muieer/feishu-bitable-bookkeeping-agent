# 验证方法与验收范围

验证完整消息理解、独立决策与状态、集中新增、批量补充与纠错、个人分类和飞书反馈。默认使用虚构消费、FunctionModel、模拟 HTTP 和模拟 CLI，禁止向真实账本写测试数据。本次重构真实 LLM 请求总次数为 **0**。

## 离线验证

在项目根目录执行：

```bash
.venv/bin/python -m pytest -q
.venv/bin/ruff check src tests
.venv/bin/ruff format --check src tests
```

测试配置 `LLM_HTTP_REQUEST_LIMIT=0`，并阻断 `httpx2.AsyncHTTPTransport` 的真实网络传输。HTTP 协议和 SDK 重试测试使用 MockTransport，所有表格操作通过临时模拟 CLI 子进程运行；不会访问真实飞书、真实模型或真实消费记录。测试文件纳入版本控制，虚构分类知识由临时夹具提供，个人知识文件不参与默认测试。

Pydantic AI、Channel SDK、子进程调用、JSON 去重文件、远端字段校验代码、日志及 Card 2.0 投影使用实际实现。模拟模型返回的语义结果用于验证执行合同，不能证明真实模型能正确理解全部自然语言。

## 核心场景

| 场景 | 必须验证的行为 |
| --- | --- |
| `咖啡18元外卖25元`，或用不同逗号、句号、分号、换行表达 | 完整消息交给模型，一次决策运行；合法新增仅一次批量接口 |
| `咖啡和面包合计30元` | 只创建一笔合计交易，不分别创建明细和总额 |
| `咖啡18元，不对是20元` | 只创建最终事实20元的一笔，不额外修改其他账单 |
| 相同消费出现两次 | 通过原文出现位置区别真实独立交易；重复模型来源不能创建两次 |
| 边界不确定或分类有歧义 | 独立追问，不猜测拆分、不遗漏其他明确项目 |
| 一笔负数、无效日期或非法分类，另一笔合法 | 合法项目继续；无效项目独立待补充 |
| 普通分类与非记账消息 | 一次推理，无历史调用，无无关业务工具 |
| 多笔需要同一个历史关键词 | 关键词只读查询一次，统一二次补分类；首轮明确项目保持不变 |
| 二次输出试图改金额、日期、描述、目标或集合 | 拒绝变化，未确定项目追问，首轮合法项目继续 |
| `午饭30元晚饭40元` 后回复 `堂食` | 多目标时追问；不能随意选一笔 |
| 最新编号分别补充多笔 | 原编号映射固定，补齐的合法新增一次集中写入 |
| 明确自然语言指定「晚饭」 | 唯一匹配允许关联，多目标或其他用户会话 ID 不允许 |
| 多轮补金额、用途和分类 | 原文与已知事实不丢失；成功项目不重复新增 |
| 跨天补充或明确修改「日期是昨天」 | 补充沿用原日期基准；明确修改相对日期用当前消息时间 |
| 追问后新消费或闲聊 | 旧待办继续保留，新消费不继承旧信息 |
| 最近账单纠错、两笔最新编号纠错 | 仅修改允许目标和明确字段，编号不因前一项执行重新排列 |
| 仅提及账单或伪造编号、历史列表编号 | 不执行修改，不回退到最近账单 |
| 新增、纠错与长期偏好混合 | 合法项独立执行；偏好不改变历史账单 |
| 未完成修改继续补充或取消 | 修改草稿不转为新增；取消仅丢弃未提交草稿 |
| 修改前发现外部修改或记录消失 | 不覆盖手工变更，不提交修改 |
| 修改响应缺少 ID、ID 类型或数量异常、目标不匹配或字段被忽略 | 提示待核对，不推定成功，不自动重写 |
| 真实格式 NDJSON manifest 不含 `ok` 字段 | 正常读取修改前的纠错目标及历史；来源、文件路径、行数或大小异常仍拒绝 |
| 新增响应缺少 ID、ID 重复、数量异常或字段被忽略 | 整批待核对，不推定成功，不自动重写 |
| 新增或修改成功响应返回准确完整的 ID，读回可能暂时不可见或异常 | 按响应确认结果，不调用写后回读；保留逐笔 ID、成功快照、去重及后续纠错 |
| 去重保存失败、写入超时、取消或重启 | 写前持久化逐笔保留；已有保留不重复执行；区分未执行与待核对 |
| 远端成功、本地成功保存失败 | 当前会话保留确认事实并提示保存失败；重启后仍不重放 |
| 卡片更新、结果送达或日志失败 | 回复失败不重复记账；日志失败停止新请求和写入，已提交新增和修改继续解析并校验写入响应 |
| 会话过期或重启 | 短期目标及编号失效，长期偏好和写入去重继续有效 |
| TEST_MODE | 不新增或修改真实记录；保留分类及字段验证，显示准备记账；偏好仍按既有规则保存 |

## 真实模型核验的请求额度

如另行核验真实模型语义，使用独立预算文件，并在启动前设置总额度。预算文件存在时继续原计数，不删除或改写计数以绕过上限。本次任务的总上限为 15 次真实模型 HTTP 请求，包含第二阶段、输出重试、SDK 自动重试、HTTP 自动重定向及连接失败的发送尝试。

```bash
export LLM_HTTP_REQUEST_LIMIT=15
export LLM_HTTP_BUDGET_PATH=.runtime/semantic-verification-budget.json
```

计数在每次发送前持久化，额度不足时请求不会送出；文件锁协调多个客户端或进程，重启继续计数。未配置额度时正常生产不限制请求。离线测试预算始终为 0，不需要真实密钥。

仅核验语义时调用 `DecisionEngine` 并模拟全部历史查询；不要调用生产 `BookkeepingService.reply` 或 `--ask`，以免写入真实账本。`TEST_MODE=true` 仍会调用模型、只读飞书，也会保存合法长期偏好，不能代替完整的无副作用模拟。

## 真实飞书界面和权限验收

本次未进行真实飞书 UI 或远端读写验收。后续若使用专用测试账本，先确认完整分类知识、目标表结构、CLI 身份及新增/修改权限。只读本地检查使用 `bookkeeping-agent --check`，远端字段检查使用 `--check-remote`；这两个入口不调用模型、不写账单。

使用支持 Card 2.0 的飞书桌面和移动端核对：立即回复原消息的卡片和单个 `OneSecond` 表情；同会话等待顺序；真实执行环节与逐笔确认数；默认折叠过程；单笔简洁结果；多笔汇总与准确编号、状态和追问；长描述及 Markdown/HTML 字符按纯文本展示；结束后不被旧进度覆盖。

新增和修改均依据写入接口的成功标识及返回记录 ID 确认，不再进行写后回读。接口当前不返回逐笔字段明细；响应缺失、目标不匹配、字段被忽略或写入超时时，应用显示待核对。人工核对表格，不通过重发消费或删除去重文件试探结果。
