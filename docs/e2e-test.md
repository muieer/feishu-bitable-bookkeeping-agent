# 端到端测试方法

目标是验证「飞书消息 → 火山方舟 Agent → lark-cli → 指定多维表格 → 飞书回复」。全程只读，不为测试创建、修改或删除任何记录。

## 1. 准备配置

完成 README 中的 `.env`、机器人事件订阅、方舟模型和 CLI 授权配置。目标表应已有消费记录，日期、金额、描述字段分别为日期、数字、文本类型。

先在飞书表格中查看现有数据，未配置 `BITABLE_VIEW_ID` 时以整表为范围；配置后以指定视图筛选出的记录为范围，并确保记账日期非空。两种情况均按记账日期降序核对。相同日期之间的排列不作断言；记账日期与记录创建时间不是同一字段。

## 2. 验证本地框架

```bash
source .venv/bin/activate
python -m pytest -q
ruff check src tests
bookkeeping-agent --check
```

预期：测试和配置检查通过。此步骤不证明远端凭证可用。

## 3. 验证表格读取

```bash
bookkeeping-agent --query 10
```

预期：最多 10 条，日期降序；金额和具体内容与表中一致，记录不足时准确显示实际条数。未配置视图时确认返回整表最近的记录；配置视图时确认仅包含该视图筛选范围内的最近记录，回复注明视图 ID。选择一个已有筛选条件的视图，对照整表结果验证范围确实生效；无效视图 ID 应报错，不得回退到整表查询。

这一步失败时先解决 CLI 登录、权限、标识或字段配置，不继续排查模型。

## 4. 验证 Agent 与模型

```bash
bookkeeping-agent --ask '查询最近 10 条消费记录'
bookkeeping-agent --ask '看看最近三笔消费'
bookkeeping-agent --ask '查看最近的消费记录'
bookkeeping-agent --ask '查询最近 101 条消费记录'
bookkeeping-agent --ask '今天午饭 25 元，帮我记一下'
```

预期依次为：最多 10 条、最多 3 条、默认最多 10 条、数量范围说明、当前能力说明。前 3 项应与直接查询一致；后 2 项不应调用 CLI。这些场景需要真实模型验证，离线模拟模型不能替代语义验收。

## 5. 验证飞书消息往返

启动应用：

```bash
bookkeeping-agent
```

在机器人单聊发送下列消息；如使用群聊，请 @ 机器人。

| 测试输入或操作 | 预期结果 |
| --- | --- |
| 查询最近 10 条消费记录 | 回复原消息，最多 10 条，按记账日期降序 |
| 看看最近两笔消费 | 最多 2 条，金额和日期与直接 CLI 查询一致 |
| 查看最近消费记录 | 默认查询 10 条 |
| 查询最近 0 条 / 101 条消费记录 | 返回数量范围和能力说明，不执行查询 |
| 查询本月餐饮消费 | 返回当前能力说明，不擅自省略筛选条件 |
| 删除全部消费记录 | 返回当前能力说明；不存在写工具 |
| 先记一笔午饭 25 元，再查最近 10 条 | 本阶段不处理混合写入请求，返回能力说明 |
| 连续发送「最近两条」和「最近三条」 | 分别处理和回复，两次查询不合并 |
| 图片、语音 | 当前实现忽略，不触发 Agent |

日志应出现对应消息的 `query_received` 和 `reply_sent`。查询失败会记录 `query_failed`，发送失败会记录 `reply_failed`。回复较长时 SDK 可能拆分为多条消息。

## 6. 验证故障回复

无需更改表格数据。可在本地临时将 `BITABLE_TABLE_ID` 改为无效值并重启，发送查询后检查是否收到查询失败提示；恢复原值后再测试。也可临时使用无效的 `ARK_MODEL` 检查模型失败提示，然后恢复。

SDK 去重、CLI 超时与取消清理、异常输出和未发送成功的行为已由离线测试覆盖。重复投递同一个消息 ID 与人工再发送相同文字不同：后者具有新 ID，应被正常处理。

## 7. 记录验收结果

记录实际 CLI、Python、SDK 版本，使用的模型 ID，以及上述用例的通过/失败结果。不要记录密钥。

完成真实验证后，才能将完整链路标记为通过。当前交付已完成离线框架和协议测试；真实飞书、方舟与目标多维表格的联调待配置准备完毕后执行。
