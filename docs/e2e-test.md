# 记账 MVP 验收方法

本次验收覆盖「飞书消息 → 火山方舟 → 结构化与业务校验 → lark-cli 写入 → 飞书回复」，以及即时纠错、明确长期偏好和异常处理。正式系统提示词未准备好时，只进行离线和只读验证，不启动生产记账测试。

## 1. 本地与只读检查

在项目根目录执行：

```bash
source .venv/bin/activate
python -m pytest -q
ruff check src tests
ruff format --check src tests
bookkeeping-agent --check
bookkeeping-agent --check-remote
```

预期：离线检查通过；本地知识与表 ID 匹配；远端字段及完整分类选项通过校验。提示词为空时，本地检查明确显示 Agent 尚不能启动。

离线测试使用模拟模型决策、模拟 HTTP 和模拟 CLI 子进程，不修改真实账单。SDK、Pydantic AI、进程调用和 JSON 文件流程采用真实组件。模型语义与远端新增、修改权限仍需真实验收。

## 2. 准备提示词与会话

将正式提示词放入 `prompts/system.md`，或配置 `AGENT_SYSTEM_PROMPT_PATH`。接入合同见 [提示词说明](../prompts/README.md)。确认 CLI 身份对目标表具有新增及修改记录权限。

需要连续追问或即时纠错时，使用 `bookkeeping-agent --interactive` 或启动机器人长连接 `bookkeeping-agent`。单次 `--ask` 退出后会丢失短期会话，不能跨进程纠错。

以下真实测试会写入配置的表格。每笔新增后记录其 ID，核对消费日期、金额、描述和完整分类路径。不要仅凭回复文字判断远端数据正确。

## 3. 新增、分类和非记账反馈验收

| 输入 | 验收结果 |
| --- | --- |
| 今天外卖午饭 25 元 | 创建一条，日期为消息发送日期，分类「饮食 / 外卖」 |
| 昨天咖啡 18 元 | 创建一条，日期为消息发送时间在配置时区的前一天，分类「饮食 / 咖啡」 |
| 给母亲买咖啡 30 元 | 按个人用途规则分类为「人情往来 / 父母」 |
| 停车费 10 元 | 分类「交通通信 / 汽车 / 停车费」 |
| 今天午饭 25 元 | 根据现有个人规则追问堂食还是外卖，未回答前不写入 |
| 今天买了点东西 | 追问缺失内容、金额及必要分类信息，未回答前不写入 |
| 堂食（接在午饭追问后） | 合并上一轮事实，只创建一条原消费账单 |
| 咖啡 18 元，午饭外卖 25 元 | 提示分别发送，不只记一笔或合并金额 |
| 明天准备买咖啡 / 这个商品售价 18 元 / 查询消费 / 闲聊 | 简短回复「这条消息未涉及实际消费，本次未记账。」，无历史或写入 CLI 调用，数据无变化 |
| 图片、语音 | 忽略，不调用模型 |

确认历史检索仅在模型确有需要时进行；明确规则不能被历史案例覆盖。午饭示例的追问遵循现有规则，不能为满足「自动记账」示例而猜测用餐方式。

## 4. 纠错、偏好与隔离

| 操作 | 验收结果 |
| --- | --- |
| 新增后发送「不对，刚才是 28 元」 | 修改该用户、该会话最近账单金额，不创建新行 |
| 指出最近汽车消费实际是咖啡消费 | 合法分类修改后，原三级分类清空 |
| 另一用户或另一会话发送纠错 | 不能修改前一用户或前一会话账单 |
| 表格中手动修改最近账单后，再发送纠错 | 停止覆盖并提示核对 |
| 只纠正一次分类 | `preferences.json` 不新增长期偏好 |
| 以后豆浆都归类为食品 | 保存完整合法路径「饮食 / 食品」，不修改已有账单 |
| 随后发送「豆浆 5 元」 | 按新的明确偏好分类；重启后偏好仍有效 |
| 追问在午夜前发生，补充在午夜后发送 | 原消费日期不因回答跨日而改变 |
| 追问后另发一笔新消费 | 新账单采用新消息的发送日期 |

## 5. 去重与故障

消息 ID 相同的重投递应避免再次执行；人工重新发送相同文字具有新消息 ID，按新的消费处理，不等同于平台重投递。

离线测试已覆盖同一消息重复投递、回复失败后的重启、写入中取消、写入成功后本地日志失败，以及同一会话新增后纠错的顺序。真实故障测试应先检查目标与预期影响，再临时使用不可写的测试配置；不要通过重新发送生产消费验证是否写入。

| 场景 | 验收结果 |
| --- | --- |
| CLI 明确失败 | 不反馈记账成功 |
| 创建超时、异常返回、缺少唯一记录 ID | 提示核对，不自动重复创建 |
| 修改提交后尚未核对到完整结果 | 不宣称修改完成，提示核对 |
| 模型失败或理解阶段超时 | 安全错误回复，不执行写入 |
| 去重日志无法保存 | 不提交新写入 |
| 创建成功但飞书回复发送失败 | 保留成功日志，重投递不再次创建 |
| 应用重启 | 最近对话和纠错上下文丢失；已保存偏好和写入去重仍有效 |

## 6. 运行卡片与过程展示验收

使用支持 Card 2.0 的飞书桌面端和移动端验收以下内容。普通新增和修改可复用前面的测试消费，避免为界面验收重复写入相同账单。

| 场景 | 验收结果 |
| --- | --- |
| 收到有效文字消息 | 立即以卡片回复原消息，并只添加一个 `OneSecond` 表情 |
| 上一条消息尚未完成时再发消息 | 后一条先收到等待卡片，轮到后切换为处理中，业务顺序不变 |
| 模型或查询仍在运行 | 当前动作与实际环节一致，耗时持续更新，不提前显示成功 |
| 执行过程 | 默认收起，展开后只出现实际执行的关键步骤，完成之后才标记完成 |
| 字号与留白 | 过程标题与步骤比正文小一级，状态、耗时、当前动作和结果保持正文字号，无独立大标题，四边内边距一致 |
| 新增或纠错成功 | 结果在执行过程之后，按「日期｜一级分类｜二级分类｜三级分类｜具体｜金额」以单段正文显示 |
| 需要追问 | 问题在最下方，与「本次尚未记账」合并成一段正文 |
| 非记账、偏好保存、失败和待核对 | 分别显示准确结果，已提交但未确认时提醒先核对、勿重复发送 |
| 长描述、换行及 Markdown 或 HTML 字符 | 换行转为空格，正文完整、不截断；其余字符以纯文本展示，移动端自然换行，不触发提及或改变排版 |
| 处理结束 | 停止刷新耗时和步骤，旧进度不覆盖最终结果 |
| 卡片更新失败 | 尝试送达最终结果，业务写入次数不增加 |

## 7. 批量记账验收

在同一会话中依次执行，使用账本中实际合法的分类路径核对结果：

1. 发送「外卖25元。午饭30元。打车18元。」。确认完整账单先写入，午饭保留金额与消费日期并追问用餐方式，结果为成功 2 笔、待补充 1 笔。
2. 回复「堂食。第一笔金额是20元。」。确认只新增午饭、修改外卖金额，打车不变；卡片只展示本次处理的外卖和午饭。
3. 回复「第 2 个，金额是20元」。确认修改的是最新列表中的午饭，不是更早列表的打车，且没有新增记录。随后回复「第一笔账单，日期是昨天」，确认修改最新列表唯一账单的日期。
4. 使用两笔待补充账单，先补充其中一笔。确认最新列表保留另一笔问题并重新编号，下一轮能按新编号继续。
5. 检查批量卡片的同类步骤只出现一次，已处理数量持续更新，执行过程默认折叠。成功与待补充、待处理或待核对数量应与实际结果一致。

跨天补充、同批次单笔写入不确定、整条消息重投递、进程中断、中文编号和旧编号禁止回退由离线测试覆盖。模型语义和真实飞书卡片效果仍需在实际环境验收，不能仅凭离线测试认定通过。

## 8. 验收记录

记录实际 Python、CLI、SDK、Pydantic AI 和模型版本，提示词版本，测试输入、消息 ID、账单 ID、实际字段及通过/失败结果。不要记录密钥。

2026-10-11 批量追问修复验收：最终相关离线回归 147 项通过，包括生产日志中 `clarify + expense=null` 的重放、最新列表编号、跨天补充和防重复写入。静态检查、格式检查和差异检查通过。此前一次全量测试为 199 项通过、7 项失败：其中 6 项是已有知识上下文格式及日志断言差异；另 1 项是 CLI 超时测试未及时产生捕获文件，单独复跑通过。

经用户授权，使用项目配置的火山方舟模型、提示词、个人分类知识及合成消费进行只读语义核验。5 类样本均取得符合预期的结果：午饭追问保留金额、无编号「堂食」关联待补充午饭、第 2 个修改金额、第一笔修改为昨天、编号相关的天气问题不产生操作。追加跨天样本后，发现并修复了短回答被误作无关联新消费的问题；最终跨天核验关联原待办，日期省略后由程序保留原日期。输出校验同时要求完整的关联字段，并明确空目标必须返回 JSON `null`；校验失败的输出不会进入写入流程。

这些检查未写入真实账本或发送飞书消息。真实飞书卡片展示及新增、纠错往返仍需实际环境验收；有限语义样本通过不代表所有自然语言表达均已覆盖。
