# 飞书记账智能体：开发与运行指南

本项目在本地运行一个 Python 应用。用户向飞书机器人发送实际消费信息，Pydantic AI 调用火山方舟理解意图并依据个人分类知识生成结构化决策，程序校验后使用官方 `lark-cli` 写入现有多维表格，再回复结果。

本文保留安装配置、运行排查与二次开发所需的实现说明。项目价值与技术设计概览见 [项目首页](../README.md)。

当前以完整消息为单位，统一支持单笔和多笔新增、批量补充与纠错、明确的长期分类偏好、信息追问及混合操作。仓库已提供默认系统提示词 `prompts/system.md`。文件缺失或为空时 Agent 停止启动；本地检查与只读表格诊断仍可运行。

## 能力与行为

| 消息或场景 | 行为 |
| --- | --- |
| 今天外卖午饭 25 元 | 字段和分类明确时直接记账 |
| 昨天咖啡 18 元 | 以消息发送时间解析日期，依据个人规则分类 |
| 给母亲买咖啡 30 元 | 明确的人情目的优先，按个人规则归入「人情往来 / 父母」 |
| 今天午饭 25 元 | 现有规则不允许仅凭「午饭」推断堂食或外卖，先追问 |
| 今天买了点东西 | 追问金额、消费内容和必要的分类依据，不写入 |
| 不对，刚才是 28 元 | 只修改当前用户、当前会话最近成功账单 |
| 以后豆浆都归类为食品 | 合法分类路径明确时，保存长期偏好；后续分类读取该偏好 |
| 明天打算喝咖啡 / 这个商品多少钱 / 查询统计 / 闲聊 | 不调用历史或写入工具，卡片显示本次未记账 |
| 一条完整消息包含多笔消费，无需特定标点 | 一次理解、逐笔校验，合法新增集中批量写入，其他账单保留并追问 |
| 3是堂食 / 2的金额改成20元 | 只按最新列表编号补充或纠错，支持「第二笔」「第 2 个」等表达；不查找历史编号 |
| 图片、语音、机器人消息 | 忽略 |
| 写入超时、返回异常或不能逐笔对应记录 ID | 提示结果待核对，不反馈记账成功，不自动重试 |

自然语言理解和上述分类判断由正式提示词、模型及个人知识共同决定。程序独立校验金额、日期、分类层级与执行目标，离线测试不能代替真实模型语义验收。批量结果与编号规则见 [系统架构与工作流程](系统架构与工作流程.md#最新编号与纠错)。

## 安装与配置

需要 Python 3.11 或以上版本、官方 `lark-cli` 和支持 Function Calling 的火山方舟模型。核心依赖沿用已验证版本：`lark-channel-sdk==1.4.0`、`pydantic-ai-slim[openai]==2.54.0`。

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock.txt
```

已有 `.venv` 时直接激活。在项目根目录运行应用，配置及文件的相对路径均基于启动目录。

首次配置时复制 `.env.example`；已有 `.env` 时只补充需要覆盖的配置，不覆盖现有密钥。

```bash
cp .env.example .env
```

| 配置项 | 用途与默认值 |
| --- | --- |
| `LARK_APP_ID`、`LARK_APP_SECRET` | 飞书机器人凭证，必填 |
| `ARK_API_KEY`、`ARK_MODEL` | 方舟 API Key 和模型或推理接入点 ID，必填 |
| `ARK_BASE_URL` | 默认为 `https://ark.cn-beijing.volces.com/api/v3` |
| `BITABLE_BASE_TOKEN`、`BITABLE_TABLE_ID` | 现有 Base token 和表 ID，必填；表 ID 必须与知识文件一致 |
| `TEST_MODE` | 布尔值，默认 `false`；设为 `true` 时不新增或修改多维表格记录，文字和卡片结果显示「准备记账」。仍执行消息理解、校验及只读查询，长期分类偏好仍按原流程保存 |
| `BITABLE_DATE_FIELD`、`BITABLE_AMOUNT_FIELD`、`BITABLE_DESCRIPTION_FIELD` | 默认「记账日期」「金额」「具体」 |
| `BITABLE_CATEGORY1_FIELD`、`BITABLE_CATEGORY2_FIELD`、`BITABLE_CATEGORY3_FIELD` | 默认「一级分类」「二级分类」「三级分类」 |
| `AGENT_SYSTEM_PROMPT_PATH` | 默认 `prompts/system.md`，UTF-8；也可配置绝对路径 |
| `CATEGORIES_PATH`、`RULES_PATH`、`SCHEMA_PATH` | 默认 `knowledge/categories.json`、`knowledge/rules.json`、`knowledge/schema.json` |
| `PREFERENCES_PATH` | 默认 `knowledge/preferences.json`，首次更新长期偏好时自动创建 |
| `OPERATION_JOURNAL_PATH` | 默认 `.runtime/operations.json`，写入去重日志 |
| `LOG_FILE_PATH` | 默认 `logs/service.log`，总运行日志；已有显式配置继续生效，父目录自动创建 |
| `MESSAGE_LOG_DIR` | 默认 `logs`，所有消息日志统一保存在其 `messages/` 子目录；支持绝对路径 |
| `CONTEXT_TTL_SECONDS` | 默认 `1800`；追问、最近账单和最近对话的内存有效期 |
| `DISPLAY_TIMEZONE` | 默认 `Asia/Shanghai`；用于解析和写入日期 |
| `LARK_CLI_PATH`、`LARK_CLI_IDENTITY` | 默认 `lark-cli`、`user` |
| `CLI_TIMEOUT_SECONDS` | 默认 `30`；每次 CLI 调用的超时 |
| `LLM_HTTP_REQUEST_LIMIT`、`LLM_HTTP_BUDGET_PATH` | 可选 HTTP 请求发送额度与持久化计数文件；包含自动重试，验证时可设为 `0`，正常生产默认不限制 |
| `AGENT_TIMEOUT_SECONDS` | 默认 `90`；模型理解阶段的超时，不中断已提交的写入 |
| `BITABLE_VIEW_ID` | 仅用于 `--query` 只读诊断；记账和历史分类检索针对整张目标表 |

默认分类知识读取本地 `knowledge` 文件。仓库提供三个结构一致的虚构模板：`categories.example.json`（分类树）、`rules.example.json`（分类规则）和 `schema.example.json`（表结构）。模板包含演示分类与虚构消费例句，历史样本数均为 0，表 ID 和字段 ID 均为示例占位值。个人知识文件及运行时生成的 `preferences.json` 继续由 Git 忽略。

新环境中，确认对应的本地文件尚不存在后，复制模板：

```bash
cp knowledge/categories.example.json knowledge/categories.json
cp knowledge/rules.example.json knowledge/rules.json
cp knowledge/schema.example.json knowledge/schema.json
```

使用前，将 `categories.json` 和 `schema.json` 中的表 ID 与 `.env` 的 `BITABLE_TABLE_ID` 设为同一真实目标表 ID，并将表结构中的字段 ID、名称、类型和选项调整为目标表的实际配置。分类树、规则路径及表格分类选项须保持一致，规则的 `compatible_categories_version` 须与分类树的 `version` 一致。已有个人知识文件时保留原文件，不要用模板覆盖。

## 系统提示词

仓库已提供默认系统提示词。需要调整时，编辑以下 UTF-8 文件，或通过 `AGENT_SYSTEM_PROMPT_PATH` 指定其他文件：

```text
prompts/system.md
```

应用在启动 Agent 时读取文件，作为 Pydantic AI 的 `system_prompt`。修改提示词后重启应用。代码没有内置替代业务提示词。提示词需要遵守的输出与上下文接口见 [提示词接入说明](../prompts/README.md)；分类树、规则、长期偏好、消息时间和短期上下文由程序每轮提供，无需复制进提示词。

## 飞书与方舟准备

飞书自建应用需开启机器人能力、接收与发送消息权限、更新消息权限 `im:message:update`，以及添加消息表情回复权限 `im:message.reactions:write_only`，采用 WebSocket 长连接并订阅 `im.message.receive_v1`，发布版本使配置生效。单聊直接发送，群聊按 SDK 配置 @ 机器人。

机器人收到符合处理条件的用户文字消息后，会立即以 Card 2.0 卡片回复原消息，并添加一个「稍等」（`OneSecond`）表情。初始卡片显示「已收到」；同一会话的后续消息先显示「已收到 · 等待中」，业务仍按接收顺序处理。表情请求与卡片请求并行，表情反馈不阻塞记账。

运行时，卡片按状态与耗时、当前动作、执行过程的顺序展示，累计步骤放在默认收起的「执行过程」面板中。执行过程标题与步骤使用比正文小一级的字号；状态与步骤使用灰色，其余内容保持正文字号，不使用大标题。过程只展示实际发生的环节，包括理解消息与确定分类、必要的历史分类查询、账单校验、表格检查、纠错目标核对、新增或修改账单、保存分类偏好；不会展示模型内部推理、原始 JSON 或命令参数。普通更新最短间隔为 1 秒，无新动作时每 5 秒刷新耗时。

处理结束后，结果位于执行过程之后，以单段正文展示，不再显示独立标题。记账或修改成功时，按「日期｜一级分类｜二级分类｜三级分类｜具体｜金额」显示，日期使用 `YYYY/MM/DD`，三级分类为空时省略，金额省略小数末尾的零并紧接「元」；需要补充信息时，将问题与「本次尚未记账」合并为一段；非记账消息说明本次未记账。正文中的换行转为空格，长内容随卡片宽度自然换行，Markdown 和标签字符均按纯文本展示。处理失败、写入待核对，以及表格成功但本地状态保存失败分别反馈，不提前宣称成功。结束后停止刷新耗时和步骤。

卡片发送和更新请求的应用级等待上限为 3 秒。中间更新失败后，在下一次更新尝试发送最新内容；最终更新失败时，尝试补发完整结果卡片，再失败则尝试文字回复。反馈失败不重试业务写入。可捕获的中断会尽力结束卡片；进程被强制终止或网络完全不可用时，卡片可能保留最后一次成功更新的状态。Card 2.0 的完整展示需使用支持该版本的飞书客户端。

CLI 登录态与机器人凭证独立，应用不会自动登录或切换身份。CLI 使用的用户必须能够读取目标表，并具备新增、修改记录的权限。按 CLI 实际返回的 `missing_scopes` 补充授权。可在交互终端检查：

```bash
lark-cli --version
lark-cli auth status --json --verify
```

方舟使用 OpenAI 兼容的 Chat Completions 接口。模型须支持结构化结果所需的 Function Calling，以及包含多个决策的结构化输出。

## 启动与检查

程序将总运行日志同时输出到终端和 `LOG_FILE_PATH` 指定的文件，以 UTF-8 编码追加，保留已有内容。在项目根目录启动时，默认总日志为 `logs/service.log`，消息日志统一保存在 `logs/messages/`。启动日志中的 `application_started` 显示两个路径的实际绝对位置。相对路径基于启动目录；已有 `.env` 显式配置的 `LOG_FILE_PATH` 继续生效。日志目录或文件不可用时，程序提示错误并停止启动。修改配置或程序后需重启。

总日志记录启动、连接、消息日志路径、回复结果和日志系统错误。业务日志记录 INFO 及以上级别，第三方日志默认记录 WARNING 及以上级别。无需再将终端输出重定向到同一个日志文件，以免重复记录。

```bash
# 本地配置、分类树、规则和附件结构；提示词空缺会明确提示，不连接远端。
bookkeeping-agent --check

# 只读核对真实字段及完整分类选项，不调用模型、不写入。
bookkeeping-agent --check-remote

# 保留原 Demo 的只读诊断，不向机器人开放查询功能。
bookkeeping-agent --query 10

# 配置完成后，启动飞书长连接。
bookkeeping-agent
```

终端会话会实际写入配置的表格。连续交互支持追问与纠错；单条模式的会话在退出后丢失。

```bash
bookkeeping-agent --interactive
bookkeeping-agent --ask '今天外卖午饭25元'
```

也可使用 `python -m bookkeeping_agent`。终端每次输入有新消息 ID，重新输入相同文字会作为新的消费处理。

## 按消息排查完整链路

所有消息日志统一保存在 `MESSAGE_LOG_DIR/messages/`，默认路径为 `logs/messages/`，不再按消息创建子目录。每次消息投递创建一个可直接阅读的 `.log` 文件，文件名采用 `yyyyMMdd_HH:mm_ss.log`，例如 `20261010_14:30_05.log`，时间使用 `DISPLAY_TIMEZONE`。若文件名已存在，按秒递增至可用文件名，避免不同消息混写；日志内容中的时间戳保留实际记录时间。单次投递的后续记录追加到同一文件，重投递或重启后创建新文件。缺少消息 ID 时使用事件 ID；两者都缺失时生成诊断 ID。应用不迁移旧格式日志，不补造历史日志，不自动删除日志；`logs/` 已加入 Git 忽略规则。

每个事件包含时间、阶段、状态、累计耗时和缩进展开的 JSON 明细；有开始与结束的操作还记录单次耗时。`delivery_id` 区分投递，`agent_run_id` 区分 Agent run，`phase` 区分意图判断和历史补全，`loop`、`http_attempt`、`tool_call_id` 关联循环、HTTP 尝试和工具调用。消息正文和业务结果不截断，金额保留精度。日志按文件串行追加并刷新，业务写入前的检查点执行落盘同步。

| 链路 | 日志内容 |
| --- | --- |
| 收消息与会话 | SDK 原始事件、规范化消息、公开拒绝原因、应用忽略及业务去重原因、会话排队和锁等待、上下文过期、处理前后会话状态、日期基准与待追问信息 |
| Agent run | 用户输入、传入历史、上下文、模型配置、输出 Schema、重试及用量限制；实际 system prompt 和 instructions、输出工具、完整消息决策及历史补全的触发原因 |
| Agent loop | `UserPromptNode`、`ModelRequestNode`、`CallToolsNode` 开始、结束、耗时与转换；普通函数工具及输出工具的参数、校验、执行、结果和反馈；校验错误位置、类型和说明；完整重试反馈与再次请求历史 |
| 模型通信 | `agent.model_request` 保存 runtime 请求上下文；`llm.http_request` 保存实际 URL、方法、脱敏请求头和完整正文；`llm.http_response` 保存实际状态、响应头、请求 ID 和完整正文；`agent.model_response` 保存 provider 解析后的完整 `ModelResponse` |
| Run 结束 | 输出、累计请求数、工具调用数、token 用量与耗时；失败、超时、取消、用量限制；每次 run 在成功、失败和取消时补存完整内部消息历史 |
| 业务与 CLI | 决策分支、字段合并、金额／日期／分类校验、历史查询、远端字段核对、纠错与偏好保存；命令参数、完整载荷、stdout、stderr、退出码、临时返回文件内容、写入结果核对与去重状态变化 |
| 回复 | 生成结果、静默原因、实际发送载荷与关联参数、完整 `SendResult`、发送异常；终端模式的实际输出 |

排查请求组装问题时，先对照同一 run 中的 `agent.model_request` 与 `llm.http_request`，检查消息顺序、角色、工具定义、`tool_choice` 和全部参数；再对照 `llm.http_response` 与 `agent.model_response`，检查 provider 是否正确解析文本与工具调用。观察钩子保留现有 `agent.run()`，正常返回原对象，异常保留原异常，不修复输出或增加重试。模型调用继续使用非流式请求，HTTP 超时、连接池和 SDK 重试配置沿用原行为；配置 HTTP 请求额度后，自动重试也受发送前计数限制。

SDK 原始回调发生在业务回调之前。若 SDK 静默过滤消息，日志保留 `message.raw_received` 和 `business_callback=not_observed_yet`，不推断 SDK 未公开的过滤原因。每条消息中的错误保存堆栈和原因链，不采集栈帧局部变量或完整进程环境。凭证字段及配置中的已知密钥统一替换为 `[REDACTED]`。

运行期间消息日志目录或当前日志文件被删除时，程序重新创建缺失路径并记录后续事件，不补造已删除的历史日志。权限不足、路径被普通文件占用或其他创建、追加失败时，停止后续模型调用和新的业务写入。尚未提交写入时，对可回复消息反馈「调试日志保存失败，本次未执行写入」；判定为 `ignore` 的消息也反馈日志保存失败；非文字及已处理消息仍静默结束。操作已提交时，新增和修改继续解析并校验写入响应；保存去重状态，根据确认结果反馈成功或待核对，并说明日志失败。回复已发送后日志失败，不再次发送。日志错误不会被当成模型错误，也不会触发模型或写入重试。日志不可用时，失败信息记录在终端和仍可用的总日志中。

## 分类与执行约束

- 明确的长期偏好优先于旧规则，明确规则优先于动态历史案例。不同历史记录有冲突时不能按次数投票。
- 所有分类必须形成 `categories.json` 中的完整合法路径。某个二级分类有三级分支时必须填写合法三级分类，没有分支时三级分类为空。
- 金额必须是有限正数，最多两位小数；使用 `Decimal` 校验和输出 JSON 数字，不经过 Python `float` 转换。
- 未指定日期时使用消息发送日期。回答追问时保留原始日期基准，新消费使用新消息日期。消费日期在未来时追问，不写入。
- 仅写入日期、金额、消费内容和三级分类。年份、月份、周数等公式字段，以及图片、支出频率不主动填写。
- Agent 没有模型可调用的业务工具。首轮确认消费确需历史分类时，由程序统一只读查询不同关键词，并进行仅补分类的第二次推理；模型不能调用写接口或拼接 Shell 命令。
- 写入前读取远端字段结构，补查被 CLI 截断的选项；结构或选项与本地分类知识不符时停止写入。
- 新增只依据 `+record-batch-create` 的成功响应确认，检查返回 ID 的数量、非空和唯一性，以及是否有字段被忽略；不再读取新增记录核对。
- 无编号即时纠错指向最近成功账单；编号及唯一自然语言引用支持当前用户、当前会话的指定账单。先读取目标并检查是否被外部修改，再只提交变化字段；修改成功仅依据写入响应及准确匹配目标的记录 ID 确认，不再回读；返回明细缺失、目标不匹配或字段被忽略时报告待核对。
- 偏好更新保留用户明确表达的原文证据，合法路径通过校验后原子保存到独立文件，不覆盖原始规则，也不修改已有账单。

## 去重与异常处理

SDK 去重负责重复事件。业务层在每次写入前将消息 ID 保存到本地日志，确认成功后记录结果与账单 ID。进程重启时保留该日志，最近对话和纠错上下文则允许丢失。

同一会话从理解到执行按顺序处理，同一目标表的写操作串行。CLI 通过异步子进程调用；超时或取消会终止子进程并清理临时文件。模型超时只发生在执行前。

`started` 表示操作已保留但没有完整成功记录，按结果不确定处理。对该消息的再次投递不会重新执行。已成功消息再次投递时静默忽略；回复失败也不会撤销或重复账单。业务去重文件仅保留消息 ID、操作状态和必要记录 ID；完整处理明细另存于消息日志。

遇到结果不确定时，先查看表格核对。不要删除整个 `.runtime/operations.json` 或重新发送消费来试探结果。若原消息没有重投递，服务不会主动重复发送失败的回复。

## 故障排查

- **提示词为空或无法读取**：将正式提示词放入 `AGENT_SYSTEM_PROMPT_PATH`，确认 UTF-8 编码，再重启。
- **知识校验失败**：检查表 ID、分类树版本、规则路径和 `schema.json`，不得自动新建分类选项。
- **CLI 查询失败**：先运行 `--check-remote`，再检查 CLI 身份、登录态、表格权限与网络。
- **Keychain 不可用**：在能够访问 macOS 钥匙串的本机终端运行；应用不修改 CLI 凭证存储方式。
- **消息理解失败或超时**：在对应消息文件中检查 runtime 请求、实际 HTTP 请求、原始响应、解析结果和重试原因，再判断配置、接口或 runtime 问题。此时尚未执行写入。
- **纠错提示被外部修改或结果待核对**：检查表格中的目标账单，不继续覆盖或重复创建。
- **机器人没有回复**：非记账消息会简短回复本次未记账；非文字及已处理消息会静默忽略。文字消息未收到回复时，应检查长连接、发布版本、权限和 `reply_failed` 日志。

消息日志完整保留消费正文、分类上下文、模型通信和 CLI 原始输出；凭证字段和已知密钥会脱敏。日志留存与业务去重状态独立，排查时可按总日志中的消息路径定位。
