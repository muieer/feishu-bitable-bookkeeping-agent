# 飞书记账智能体：目标与处理流程梳理

## 一、基本原则

### 1. 消费记录唯一编号

在上下文窗口的生命周期内，每条消费记录都有唯一编号，例如 `B1`、`B2`、`B3`。

- LLM 负责识别新消费和已有消费。
- 程序负责为新消费分配编号，并维护编号唯一性。
- 已有消费沿用原编号。
- 程序维护消费编号与飞书多维表格 `record_id` 的映射关系。
- 未写入的消费同样拥有唯一编号。

### 2. 每笔消费只有三种决策行为

- `create`：新增消费记录。
- `update`：更新已有消费记录。
- `clarify`：不执行写入，并说明无法写入的原因，例如分类无法判断。

`clarify` 只反馈原因，不进入连续追问流程。

### 3. 模型与程序职责分离

保留 Python + Pydantic AI 的结构化输出机制。

- **LLM**：负责消费识别、文本规范化、消费分类和操作决策。
- **程序**：负责编号分配、结构校验、业务校验、操作执行和结果反馈。

### 4. 两阶段 LLM 推理

消息处理固定分为两个 LLM 阶段：

1. 消费记录识别与规范化。
2. 消费信息推理与操作决策。

**两个阶段都必须通过明确的提示词和 Pydantic 结构化输出模型，严格约束返回的数据结构和内容。**

模型输出不直接代表写入授权，所有写入必须通过程序校验。

## 二、处理流程

### 第一步：接收用户消息

飞书机器人接收用户发送的一条完整文字消息。

### 第二步：LLM 第一次推理——消费记录识别

**输入**

- 完整用户消息。
- 上下文窗口中已有的结构化消费记录（如有）。

**模型职责**

1. 识别消息中包含的一条或多条消费记录。
2. 区分新增消费与已有消费的修改。
3. 为已有消费关联正确编号，新消费暂不分配正式编号。
4. 规范化消费文本，例如去除多余空格、将 `¥` 转换为 `元`。
5. 忽略与消费无关的内容。
6. 返回符合预定义 Schema 的结构化数据。

**示例**

假设上下文窗口中已经存在 B1：

`B1：2026/10/10｜饮食｜堂食｜早餐吃包子｜12元`

用户输入：

> 咖啡 12 元。午餐堂食 20¥。我很开心。B1 账单金额更新为 20 元。

第一次 LLM 返回：

```json
{
  "items": [
    {
      "type": "new",
      "target_id": null,
      "raw": "咖啡12元"
    },
    {
      "type": "new",
      "target_id": null,
      "raw": "午餐堂食20元"
    },
    {
      "type": "existing",
      "target_id": "B1",
      "raw": "B1账单金额更新为20元"
    }
  ]
}
```

其中：

- `new` 表示识别到新的消费记录。
- `existing` 表示识别到针对已有消费的修改。
- `target_id` 用于关联上下文中的已有消费。
- `raw` 为规范化后的本次消费或修改文本。
- 已有消费的原始结构化数据由程序根据编号关联。
- “我很开心”不进入识别结果。

**第一阶段只负责识别、关联和文本规范化，不负责分类推理或最终操作决策。**

### 第三步：程序校验与编号分配

程序检查第一次 LLM 返回的数据：

1. 数据是否满足预定义 Schema。
2. 数据类型及必填字段是否正确。
3. 已有消费编号是否真实存在且关联合法。
4. 新消费与已有消费是否存在编号或关联冲突。

通过校验后，程序按照识别顺序为新消费分配编号。

例如：

- 咖啡12元 → B2
- 午餐堂食20元 → B3
- B1账单金额更新为20元 → B1

如果未识别到任何消费记录，则终止后续流程，飞书机器人回复：

> 此次不包含消费行为。

没有消费时，不进入第二次 LLM 推理，也不执行表格业务操作。

### 第四步：LLM 第二次推理——消费信息与操作决策

**输入**

- 第一阶段经过程序校验、分配编号后的结构化消费记录。
- 消息时间及其他必要上下文。
- 上下文窗口中与消费相关的已有结构化记录（如有）。
- 完整个人分类知识库，包括分类树和个人分类规则。

**分类知识策略**

- 每次第二阶段推理均注入完整分类知识。
- 不再检索历史消费案例辅助分类。
- 不再查询或保存长期分类偏好。
- 已有消费上下文只用于理解和关联当前消费，例如更新已有账单。
- 分类依据不足时返回 `clarify`，不猜测分类。

**模型职责**

对每笔消费独立完成：

1. 推理消费日期，没有明确日期时使用原消息发送当天。
2. 根据完整个人知识库推理一、二、三级分类。
3. 判断执行 `create`、`update` 或 `clarify`。
4. 返回包含编号、行为和对应详情的严格结构化决策。

**决策示例**

假设咖啡的分类依据不足，午餐分类明确，B1 需要修改金额。

```json
{
  "decisions": [
    {
      "bill_id": "B2",
      "action": "clarify",
      "raw": "咖啡12元",
      "expense": null,
      "reason": "无法根据现有分类规则确定分类"
    },
    {
      "bill_id": "B3",
      "action": "create",
      "raw": "午餐堂食20元",
      "expense": {
        "date": "2026-10-12",
        "amount": 20,
        "description": "午餐堂食",
        "category": {
          "level1": "饮食",
          "level2": "堂食",
          "level3": null
        }
      },
      "reason": null
    },
    {
      "bill_id": "B1",
      "action": "update",
      "raw": "B1账单金额更新为20元",
      "expense": {
        "date": null,
        "amount": 20,
        "description": null,
        "category": null
      },
      "reason": null
    }
  ]
}
```

以上消费分类仅用于展示结构，实际分类必须以运行时提供的个人知识库为准。

#### 第二阶段决策约束

**1. 每笔消费独立决策**

本次消息中的不同消费记录，决策时不考虑彼此之间的联系。

每笔消费只考虑自身信息，以及与自身有关的已有消费上下文。

**2. 不同行为有严格的结构化输出约束**

`create` 和 `update` 必须返回 `expense` 对象，包含四个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `date` | date 或 null | 消费日期 |
| `amount` | Decimal 或 null | 消费金额 |
| `description` | string 或 null | 消费具体内容 |
| `category` | CategoryPath 或 null | 完整分类路径 |

`category` 必须包含：

```json
{
  "level1": "饮食",
  "level2": "堂食",
  "level3": null
}
```

一级、二级分类必须存在于个人分类树中；有三级分类时填写合法三级，没有时为 `null`。

**`create`：新增消费**

- 必须返回四个字段。
- 未知字段允许为 `null`。
- 未明确日期时，默认原消息发送当天。
- 写入前必须具有完整有效的消费信息。
- 金额必须为正数，最多两位小数。
- 分类必须为合法完整路径。

**`update`：更新已有消费**

- 必须返回四个字段。
- 只填写用户明确要求修改的字段，其他字段必须为 `null`。
- 程序从已有成功账单获取原始信息，并与修改字段合并。
- 校验合并后的完整账单。
- 实际提交时只更新发生变化的字段。

例如修改 B1 金额：

```json
{
  "date": null,
  "amount": 20,
  "description": null,
  "category": null
}
```

**`clarify`：不写入**

- 返回消费编号。
- 保留本次规范化的消费文本。
- 返回明确、具体的不写入原因。
- 不执行新增或更新，也不保存待补充账单。

**3. 严格规范化输出**

两阶段分别定义独立的 Pydantic 输出模型和提示词。

- 严格限制字段名称、数据类型及允许的枚举值。
- 必填字段不能省略，不适用的字段显式返回 `null`。
- 不允许额外字段。
- 不允许返回 Schema 之外的自由文本。
- 第二阶段只能处理第一阶段已经校验通过的消费编号。
- 不得擅自增加、删除、合并消费记录。
- 模型不能编造日期、金额、消费内容或分类信息。
- 结构校验由 Pydantic 完成，业务合法性由程序进一步校验。

**两阶段的输出结构及提示词约束是本次重构的核心。**

### 第五步：程序执行

程序根据第二阶段的结构化决策逐笔执行。

| 决策 | 执行方式 |
|---|---|
| `create` | 校验后写入飞书多维表格 |
| `update` | 核对已有记录后，只更新变化的字段 |
| `clarify` | 不写入，保留原因用于最终反馈 |

**写入状态与异常处理**

保留现有项目的逐笔状态管理和防重复写入机制：

- 每笔消费独立确认执行结果。
- 已成功写入的记录保留成功结果。
- 一笔失败不影响其他合法消费的处理。
- 写入超时或结果无法确认时，标记为「待核对」。
- 不自动重试结果不确定的写入，防止重复记账。
- 程序执行失败与模型返回的 `clarify` 严格区分。
- 更新已有账单前保留远端记录检查，避免覆盖外部修改。

### 第六步：结果显示

飞书机器人按照消费行为分组展示结果。

**正常业务分组顺序：新增 → 更新 → 澄清。**

每组内部按照消费编号以列表形式展示。

**示例**

**已记账消费记录：**

1. B2：2026/10/12｜饮食｜食品｜面包｜12元
2. B3：2026/10/12｜饮食｜堂食｜午餐｜20元

**已更新消费记录：**

1. B1：2026/10/10｜饮食｜堂食｜早餐吃包子｜20元

**以下消费记录未写入：**

1. B4：咖啡12元。原因：分类无法确定。

存在程序执行失败或写入结果不确定时，另外展示对应消费编号及实际状态，不混入模型的 `clarify` 决策。

**账单显示格式**

每笔成功新增或更新的账单统一使用：

```text
日期｜一级分类｜二级分类｜三级分类（如有）｜具体｜金额
```

没有三级分类时，省略三级分类。

**执行过程反馈**

程序执行期间：

- 只显示实时消耗的时间。
- 不显示处理阶段。
- 不显示执行明细。

处理完成后，展示最终分组结果。

## 三、两阶段 LLM 提示词设计要求

### 1. 第一阶段：消费识别提示词

**目标：准确识别全部消费记录，并输出规范化的结构化识别结果。**

提示词必须明确：

- 输入是一条完整用户消息，可能包含多笔消费、已有消费修改和无关内容。
- 识别交易数量依赖消息语义，不依赖标点或换行数量。
- 区分独立消费与单笔交易中的商品明细，不能重复识别。
- 区分新消费与已有消费修改。
- 只有明确指向已有消费时，才关联已有编号。
- 不自行分配新消费的正式编号。
- 只规范化文本表达，不改变事实或推断消费分类。
- 不遗漏、不重复、不凭空生成消费。
- 返回固定结构，不能输出自由文本。

### 2. 第二阶段：消费决策提示词

**目标：根据规范化消费信息和完整个人分类知识，为每笔消费输出准确、可校验的决策。**

提示词必须明确：

- 只能处理第一阶段传入的消费记录。
- 各笔消费独立推理，不相互影响。
- 以完整个人分类知识为分类依据。
- 不使用通用分类习惯替代个人分类规则。
- 不确定时选择 `clarify`，不能猜测。
- 新增消费必须提供完整可写入的信息。
- 更新消费只输出明确要求修改的字段。
- 不改变用户未要求修改的已有字段。
- 保持消费编号与输入一一对应。
- 严格满足各决策的 Pydantic Schema。
- 不额外生成解释文字或其他操作。

## 四、相较于当前实现的调整

### 1. 保留

- Python + Pydantic AI。
- 火山方舟模型调用机制。
- Pydantic 结构化输出和校验。
- 完整个人分类知识库。
- 飞书 Channel SDK 消息通道。
- `lark-cli` 多维表格读写。
- 程序业务校验与执行边界。
- 消费记录去重、操作状态与异常处理机制。

### 2. 调整

**LLM 推理流程**

由当前完整消息决策加按需分类补全，调整为固定两个阶段：

1. 消费记录识别与文本规范化。
2. 消费分类推理与操作决策。

**编号与上下文**

- 程序统一管理消费编号。
- 上下文窗口内每笔消费具有稳定编号。
- 已有成功消费记录以结构化形式参与相关推理。
- 程序维护编号与远端 `record_id` 的关联。

**分类机制**

- 每次第二阶段推理提供完整个人分类知识。
- 取消历史消费检索辅助分类。
- 取消长期分类偏好查询。

**决策模型**

仅保留 `create`、`update`、`clarify` 三种决策。

**结构化输出**

- 两阶段采用独立的严格输出 Schema。
- 重点完善两阶段提示词对模型行为与输出结构的约束。
- 保留现有新增和修改字段规则。

**结果反馈**

- 按行为分组显示结果。
- 写入和更新展示完整账单。
- 失败及结果不确定的消费单独标明状态。
- 处理过程中仅显示实时耗时。

### 3. 移除

- 连续追问及待补充账单机制。
- 长期分类偏好查询与保存功能。
- 历史消费分类检索及二次历史分类补全机制。
- 处理期间的阶段与明细展示。

## 五、核心流程

```text
用户发送飞书消息
        ↓
LLM 第一阶段
识别消费记录、关联已有消费、规范化文本
        ↓
程序校验与编号分配
验证结构、目标关联、编号唯一性
        ↓
LLM 第二阶段
注入完整个人分类知识
逐笔推理分类及操作决策
        ↓
程序校验和执行
create / update / clarify
逐笔确认状态，防止重复写入
        ↓
结果整理
按新增、更新、澄清分组
独立展示执行失败或待核对记录
        ↓
飞书机器人反馈最终结果
```

**核心设计：两阶段严格结构化 LLM 输出 + 程序管理消费编号 + 完整个人分类知识注入 + 三种独立决策 + 程序校验与安全执行。**
